# บทที่ 11 — แนวคิด 100M+ URL และเหตุผลที่ต้องแบ่ง Segment

**เวลาเป้าหมาย:** 4 นาที

## บทพูด

[ภาพบนจอ: แสดง Disclaimer ก่อน Diagram]

สถาปัตยกรรมของ SEO Screaming Toad ถูกออกแบบให้ต่อยอดสู่แคมเปญแบบแบ่ง Segment ที่มีมากกว่า 100 ล้าน URL ได้ในทางทฤษฎี แต่ยังไม่ใช่ความสามารถที่ผ่านการทดสอบ รับรอง หรือรับประกัน

ประโยคนี้สำคัญ เพราะการตั้งช่อง URL Ceiling เป็น 100 ล้าน ไม่ได้พิสูจน์ว่าเครื่อง Crawl ได้ 100 ล้านจริง

ถ้า Crawler เก็บคิวและผลทั้งหมดไว้ใน RAM เมื่อข้อมูลใหญ่ขึ้น เครื่องจะเริ่มช้า เสี่ยง Crash และกู้คืนยาก แนวคิดของ Toad คือเก็บ Frontier ลง Storage แบบถาวร แล้วให้ Worker เช่างานเป็นชุดขนาดจำกัด เช่นครั้งละหนึ่งหมื่นหรือหนึ่งแสน URL

การจบ Segment ไม่ได้แปลว่าเริ่ม Audit ใหม่ Campaign ยังใช้ Scope, Configuration, ตัวตนของ URL, Robots Policy, Host Delay, Retry History และ Rule Version ชุดเดิมทั้งหมด

[ภาพบนจอ: Coordinator → Durable Frontier → Host Ownership → Worker → Result Segment → Query Store]

ถ้าต้องกระจายหลายเครื่องในอนาคต Coordinator จะดูว่าใครรับผิดชอบงานไหน Worker ที่หยุดทำงานสามารถถูกแทนได้ Lease มีวันหมดอายุ และการ Commit ต้อง Idempotent เพื่อไม่ให้ Retry แล้วนับ URL ซ้ำ

เลขขนาดใหญ่ต้องมาพร้อมคุณภาพ การนับ Request หรือ Queue Event 100 ล้านครั้งไม่เท่ากับ Audit URL ที่ไม่ซ้ำ 100 ล้านหน้า ต้องพิสูจน์ตัวตน URL, หลักฐานที่เก็บ, Version ของกฎ และยืนยันว่า Frontier ไม่มีงานค้าง

หลักฐานปัจจุบันของโครงการคือ Gate ระดับหนึ่งแสน URL และการทดลอง Synthetic บน Production Path ที่หนึ่งล้านกับห้าล้าน URL ยังไม่มี Live Crawl 100 ล้าน URL
